## 实现要点

### 组件 (`LikeButton`)

- 入参：`storyId`。当前 uid 从 `AuthService.instance.currentUid` 取；未登录直接 SnackBar 提示「请先登录后再点赞」，按钮显示为未选中态。
- `StreamBuilder<bool>(stream: LikeRepository.watchHasLiked(storyId, uid))` → 驱动 `liked` 选中态。
- 点击 → `LikeRepository.toggle(storyId, uid)`，仓库内部判存在则删、不存在则建，幂等。
- 视觉：选中态朱砂 `Icons.favorite` + 朱砂淡底；未选中 `Icons.favorite_outline` + 卡片底色。
- 异常用 try/catch + SnackBar 反馈。

### 计数同步

- **客户端绝不写 `likeCount`**。T1.7 `onLikeCreated/Deleted` 触发器在父 story 上 ±1。
- 详情页 `_Stats` 直接读 `story.likeCount`，靠外层 `watchById` Stream 自动反映 1–2 秒延迟后的变化——延迟来自 CF 冷启动，正常现象。
- 卡片上的 `likeCount` 同样从 `streamSquareFeed` 自动刷新，无需手动失效。

### 不在卡片上挂 LikeButton 的原因

- 列表上「点心」按钮在 Material 上意味着 Card 内有可点子目标，与「整张卡片点进详情」的 onTap 冲突（点击事件 race）。
- demo 视频里在详情页点赞演示效果最强；列表上只读、不操作，符合「列表瞄、详情用」的常见模式。

## 设计取舍

- **乐观更新 vs Stream 驱动**：选 Stream 驱动（不本地 +1），代价是 1–2 秒延迟。优点是「单一事实来源 = Firestore」，不需要处理「本地+1 / CF 完成 / Stream 回灌」三态同步；演示中延迟可解释为「服务器结算」，可接受。
- **按钮放 `_Stats` 行而非浮动**：详情页主体是 ListView，浮动按钮 (`FloatingActionButton`) 会挡正文末段；嵌在计数行旁边视觉重心和「数字增长」联动更强。
- **`watchHasLiked` 而非一次性 `hasLiked`**：监听是「另一端取消」（如 demo 多账号场景）也能反映；流量代价是每个 story doc 一个监听，单 demo 体量在 Firestore 免费额度内。
