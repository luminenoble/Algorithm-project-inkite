## 关键设计决策

以下为相对 `d4b12f8` 之前那版（关系型扁平表）的**结构性修订**，写下来供后续维护查证：

### 1. 范式：关系型 → Firestore 原生

- 命名统一 **camelCase**，禁用 snake_case
- 用 **子集合**（subcollection）承载从属数据：
  - `stories/{storyId}/comments/{commentId}`
  - `stories/{storyId}/likes/{uid}`
- 用 **嵌套对象** 承载用户配置：`users.stats.*`、`users.unlocks.*`

### 2. 鉴权与机密分离

- 删除 `password_hash` 字段。**密码完全由 Firebase Auth 托管**，Firestore 内不应再现任何鉴权凭证（与 CLAUDE.md §3 安全条款绑定）。
- 邮箱、登录方式同理，留在 Auth 内不冗余到 `users` 文档。

### 3. 补齐缺失集合

| 集合 | 归属模块 | 之前缺失原因 |
|------|---------|--------------|
| `challenges` | P2 写作 | 原 `prompt` 表把官方挑战与自由词混在一起，时间窗、激活态字段缺失 |
| `origami` | P4 游戏化 | 核心功能"AI 折纸藏品"没有对应表 |
| `charactersCache` | 模块 G | 角色查询缓存（Wikipedia + Reddit）缺失 |

### 4. 官方挑战 vs 自由词分离

- `challenges` 集合：官方三词挑战，有 `startAt` / `endAt` / `isActive`，由运营预置
- **自由模式的随机词不入库**：客户端实时生成即可，避免无谓的写入与存储

### 5. 奖励两分

| 类型 | 数据形态 | 存储位置 |
|------|---------|----------|
| AI 折纸藏品（实例） | user × 多张 | `origami/{origamiId}` 顶层集合 |
| 魔法墨水 / 主题房间（能力） | user × 开关 | `users.unlocks.magicInk` / `users.unlocks.rooms[]` |

之前混为同一张 `reward / user_reward` 表，会让发放逻辑与查询都很别扭。

### 6. 点赞幂等：uid 作文档 ID

`stories/{storyId}/likes/{uid}` —— 同一用户对同一故事天然只能有一条记录。客户端不再需要"先查再写"避免重复点赞，规则也更易写。

### 7. 冗余计数与维护方约定

`stories.likeCount` / `commentCount` / `hotScore` 写在 story 文档上，**仅由 Cloud Functions 触发器维护**，前端禁写。这是 T1.10 安全规则收紧的依据，必须从 schema 文档层面就标清。

字段表用 `维护方` 列标注：`Client` / `CF` / `Auth`，避免后续模块开发时误写。

### 8. MVP 简化

- 移除 `parent_comment_id`（楼中楼）—— README 与 TODO 都未提及嵌套评论，避免被这个字段拖累 D12 数据层冻结
- `recommendations_count` 单维度排序换成 `hotScore`（多维加权 + 时间衰减），对接 T1.7 的排行榜公式
