## 范围

把 schema 设计里 7 个集合的读 / 写 / 监听全部封装成 Repository，对外只暴露强类型方法（入参 / 返回值都是 Dart class，不是 `Map<String, dynamic>`），P2/P3/P4 不再裸接 `cloud_firestore`。同时把"接口签名"提前冻结，让 P2/P3/P4 拿到的是稳定的方法清单——内部实现允许后续优化，但**签名 D8 起不再变动**，避免下游模块跟着改。

**不包含**：

- Cloud Functions 触发器（T1.7 负责 `likeCount` / `commentCount` / `hotScore` 维护）
- 折纸生成的客户端入口（T1.8 的 `generateOrigami` 是 Callable Function，UI 端走"调 CF"的薄封装，不在 Repository 范围）
- 分页 / 游标 / 无限滚动（demo 量级 10–50 条/集合，全量 stream 即可，T1.10 视性能补）
- 字段长度 / 枚举合法性校验（schema 层校验，已计划在 T1.10 规则收紧时一并补）
- 离线缓存策略调优（`cloud_firestore` 自带本地缓存已足够 demo）
- 集成 / 单元测试用 `fake_cloud_firestore`（demo 周期内不引入测试依赖，验收走 Emulator 手测，方法见下文）

## 设计要点

### 1. 目录与命名约定

延续 T1.5 已建立的两个并列目录：

```
lib/data/
├── models/         # 强类型数据类
└── repositories/   # 集合 CRUD/监听入口
```

命名：

- 模型类名与文档语义对齐：`Story` / `StoryComment` / `StoryLike` / `Origami` / `Challenge` / `CharacterCache`
- Repository 类名 = 模型名 + `Repository`，同 T1.5 全部走 `static final instance` 单例
- 流式方法以 `watchXxx` / `streamXxx` 命名（前者 = 单文档，后者 = 多文档集合），返回类型 `Stream<T?>` / `Stream<List<T>>`

### 2. 客户端不动 CF-only 字段

`StoryRepository.create` 与 `update` 在内部组装写入 Map 时，**禁止包含** `likeCount` / `commentCount` / `hotScore` 三个字段；如调用方传了 `Story` 实例，这些字段在 `toCreateMap()` 里被丢弃。这条与 T1.4 规则 `counterFieldsUntouched()` / `counterFieldsZeroOnCreate()` 双重对齐。

> create 时不显式写 0 也安全：规则用 `request.resource.data.get('likeCount', 0) == 0` 判定，缺省视为 0。fromFirestore 读取时 `(data['likeCount'] as num?)?.toInt() ?? 0` 兜底。

### 3. StoryRepository 排序策略

`streamSquareFeed` 暴露一个枚举 `SquareSort`：

```dart
enum SquareSort {
  hotScore,   // 排行榜：visibility=public, orderBy(hotScore desc)
  newest,     // 时间轴：visibility=public, orderBy(createdAt desc)
}
```

两条查询都基于 T1.4 已声明的 `visibility ASC + hotScore DESC` 索引；`newest` 路径只用 `visibility` 单字段过滤 + `createdAt` 排序，对 Firestore 来说不需要额外复合索引（单字段自动有索引）。

`hotScore` 字段在 T1.7 上线前对全部 story 一律是 0，排序与 `newest` 等价——这是预期行为，下游不需要做任何兼容。

### 4. LikeRepository.toggle 语义

`toggle(storyId, uid)`：

1. 读 `stories/{storyId}/likes/{uid}` 是否存在
2. 存在 → `delete`（取消点赞）
3. 不存在 → `set({createdAt: serverTimestamp()})`（点赞）

幂等性来自 schema：文档 ID 强制等于 uid，T1.4 规则 `allow create, delete: if isOwner(likeUid)`。前端不维护 `likeCount`——它由 T1.7 触发器在父 story 上 `FieldValue.increment` 维护，UI 通过 `StoryRepository.watchById` 看到变化。

`watchHasLiked(storyId, uid)` 返回 `Stream<bool>`，给"红心高亮"用。

### 5. CommentRepository.add 校验责任划分

`add(storyId, comment)` 直接把 `StoryComment` 序列化写入子集合，不在 Repository 层校验 `comment.authorId == 当前 uid`——这条由 T1.4 规则强制：

```
create: if isSignedIn() && request.resource.data.authorId == request.auth.uid
```

如果调用方传错 `authorId`，写入会被规则拒，Repository 让异常向上冒。

### 6. ChallengeRepository 单活跃挑战的取舍

schema 里 `challenges.isActive` 是 bool。`watchActive()` 实现：

```
challenges
  .where('isActive', isEqualTo: true)
  .orderBy('startAt', descending: true)
  .limit(1)
```

约定：**任意时刻 isActive=true 的 challenge ≤ 1 条**，由运营在 Console 端切换上一条为 `false` 时同步把下一条置 `true`。Repository 层不做"同时只允许一个"的强制——T1.10 收紧规则时若有必要再补，demo 期靠人工纪律即可。

### 7. OrigamiRepository 仅查询

折纸藏品全部由 T1.8 的 Cloud Function `generateOrigami` 写入；客户端**永远不调 `create`** 类方法。Repository 只暴露：

- `streamMine(ownerId)` → 展览厅按用户列出
- `watchById(origamiId)` → 单件详情

T1.4 规则已经把 `origami` 段写权限关到 0。

### 8. CharactersCacheRepository 配合模块 G 嵌入

模块 G 已自行落地 Wikipedia / Reddit 取数 + 缓存写入逻辑（具体写入方由模块 G owner 决定：直接 Admin SDK 入库 / 经 CF / 离线脚本）。本 Repository 只暴露读：

- `getByKey(characterKey)`
- `watchByKey(characterKey)`

下游 P4 在角色查询页直接用 `watchByKey` 显示 `wikiSummary` / `wikiUrl` / `redditPosts`，**不需要**关心是哪一方在写。
