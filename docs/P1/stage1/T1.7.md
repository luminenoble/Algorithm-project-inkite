## 设计要点

### 1. 技术选型

- **firebase-functions v2**：触发器（`onDocumentCreated` / `onDocumentDeleted`）与 Callable（`onCall`）都用 v2 API；v2 默认更快冷启 + 更细的 IAM 控制
- **firebase-admin 13.x**：用模块化导入 `firebase-admin/app` / `firebase-admin/firestore`
- **TypeScript 5.6+**：strict 全开
- **Node 20**（与 `firebase.json` runtime 一致）
- **Region**：`asia-east1`（与 Firestore / Storage 同区，CLAUDE.md / T1.1 已锁）
- **maxInstances: 5**：在 `setGlobalOptions` 里设硬上限。demo 体量根本碰不到 5，万一被刷也兜得住成本

### 2. 计数 + hotScore 一致性靠事务

**不**用 `FieldValue.increment` 单独走，原因：hotScore 依赖"新的 likeCount / commentCount"——增减跟分数必须同步落盘，否则两次触发之间会出现"likeCount 已加 1 但 hotScore 还没动"的中间态被 `streamSquareFeed` 读到、立马又被覆盖。

实现：

```typescript
await db.runTransaction(async (tx) => {
  const snap = await tx.get(storyRef);
  if (!snap.exists) return;
  const data = snap.data() ?? {};
  const newLikeCount    = Math.max(0, (data.likeCount    ?? 0) + likeDelta);
  const newCommentCount = Math.max(0, (data.commentCount ?? 0) + commentDelta);
  const hotScore = computeHotScore({ likeCount: newLikeCount, commentCount: newCommentCount, createdAt, now });
  tx.update(storyRef, { likeCount: newLikeCount, commentCount: newCommentCount, hotScore });
});
```

`Math.max(0, ...)` 防御：若极端时序下 delete 先于 create 触发，计数不会跑负。

demo 体量下事务冲突可忽略；高并发下 Firestore 会自动重试。

### 3. hotScore 公式

```
hotScore = likeCount * 2 + commentCount + freshness * 5
freshness = max(0, 1 - ageHours / 72)
```

- **比重**：点赞权重 2、评论权重 1（评论比点赞更"沉"，但点赞门槛更低、量级更大，2:1 在 demo 数据下分得清前后）
- **freshness**：发布后 72 小时内线性衰减至 0；新发布空 story 起点 `hotScore = 5`（≈ 2.5 个赞或 5 条评论的等效"曝光机会"），让新内容有窗口被发现
- **不引入对数项**：Reddit 那种 `log10(score)` 主要是为了把大热门和小热门拉回到一个屏幕上看；demo 数据量小，平铺线性公式更直观，演示讲解也省事
- **不做时间衰减更陡的负权**：避免老内容 hotScore 跌成负数后被排到末尾时"看不见"的诡异感

下游若想换公式，只改 `src/hotScore.ts::computeHotScore`，触发器 / Callable / 索引都不动。

### 4. `onStoryCreated` 的必要性

T1.6 `Story.toCreateMap()` 故意**不写** `likeCount / commentCount / hotScore`（让规则 `counterFieldsZeroOnCreate` 默认值匹配生效）。这意味着新文档落库时这三个字段不存在。

`streamSquareFeed(sort: hotScore)` 内部是 `orderBy('hotScore', descending: true)`——**Firestore 对 `orderBy` 字段缺失的文档会自动排除**。如果不补 `onStoryCreated`，新发布的 story 永远不会出现在排行榜里，要等首次点赞 / 评论才进榜。

`onStoryCreated` 在 story 落库后立即把三字段初始化（含 `hotScore = 5`），约 1–2 秒后该 story 即进入排行榜尾部。这个延迟对 demo 可接受、且和 Reddit / Twitter 的"新帖延迟上榜"体感一致。

### 5. `recomputeHotScores` Callable

```typescript
export const recomputeHotScores = onCall(async (request) => {
  const isEmulator = process.env.FUNCTIONS_EMULATOR === "true";
  if (!isEmulator && !request.auth) {
    throw new HttpsError('unauthenticated', '需要登录');
  }
  // 遍历 stories，按当前时间重算 hotScore，按 400 一批 batch.commit
});
```

- **生产登录即可调**：dev 期方便；T1.10 收紧时加 `request.auth.token.admin === true` 之类的 admin 校验
- **Emulator 跳过 auth**：emulator 的 Auth 不签发真实 ID Token，functions:shell 与 HTTP 直调都拿不到 `request.auth`，跳过以便本地验证不卡在鉴权
- **分批 400 条**：Firestore batch 上限 500，留余量
- **demo 体量**（≤ 50 story）→ 1 批搞定，循环开销可忽略
- **不写 user.stats**：本任务只 recompute hotScore；其他派生字段它不管
- **返回**：`{ recomputed: number }`，便于演示前控制台日志确认

**触发方式**（不在 UI 里）：

```powershell
# 方式 A（emulator，推荐）：PowerShell 直接打 HTTP（v2 onCall 要求 body 包一层 data）
Invoke-RestMethod -Uri 'http://127.0.0.1:5001/inkite-demo/asia-east1/recomputeHotScores' `
  -Method Post `
  -ContentType 'application/json' `
  -Body '{"data": {}}'
# 返回：result=@{recomputed=N}

# 方式 B（生产）：Cloud Functions Console → Functions → recomputeHotScores → Test the function
# 传 {"data": {}} 即可；生产链路 Console 会自动塞 admin auth

# 方式 C：演示当天可以临时在 Flutter「我的」页加一个隐藏按钮调它，T1.11 决定是否做
```

> `functions:shell` 对 v2 onCall 的 body 包装存在已知缺陷（wraps 不进 `data` 字段），
> 直接打 HTTP 是 emulator 下最稳的验证路径。

### 6. 与 T1.4 安全规则的搭接

Functions 用 Admin SDK 跑 → **bypass 所有安全规则**。所以触发器写 `likeCount` / `commentCount` / `hotScore` 完全无视前端被禁的限制。这是 schema §「安全规则要点」预设的分工：

- 客户端不能直写 → 防刷
- CF 触发器 / Callable 可以写 → 真实变化由服务端代笔

### 7. 错误处理

- `firebase-functions/v2` 的 `logger.warn` / `logger.error` 记日志，触发器内不抛错（抛错会触发自动重试机制，可能产生重复计数；我们用事务+Math.max(0)保护已经足够幂等）
- 若 story 文档在事务里被 `tx.get` 读出来发现不存在（用户已删 story）：直接 return，记 warn 日志，不算错误

> 触发器对调用方透明（监听 Firestore 自动跑）。Callable 暴露面：

### `recomputeHotScores`

- **类型**：HTTPS Callable（v2）
- **入参**：`{}`（无参；目前不接受过滤条件）
- **出参**：`{ recomputed: number }` —— 本次重算的 story 总数
- **鉴权**：登录用户即可（dev 期）；T1.10 后改 admin-only
- **Flutter 端调法**（**当前 demo 不接 UI，仅记录**）：

```dart
// 若日后要接，需在 pubspec 加 cloud_functions 依赖
final res = await FirebaseFunctions.instanceFor(region: 'asia-east1')
    .httpsCallable('recomputeHotScores')
    .call();
final count = (res.data['recomputed'] as num).toInt();
```

T1.7 不动 `pubspec.yaml`。

### 触发器副作用一览（P3 排行榜 / 点赞 / 评论的可见行为）

| 操作 | 客户端可观察的字段变化（≤ 2 秒延迟） |
|------|--------------------------------------|
| 客户端创建 story | story 多了 `likeCount=0` / `commentCount=0` / `hotScore=5`（freshness 衰减后会变） |
| 客户端点赞（`LikeRepository.toggle`） | story.likeCount +1，hotScore 更新 |
| 客户端取消点赞 | story.likeCount -1（min=0），hotScore 更新 |
| 客户端发评论 | story.commentCount +1，hotScore 更新 |
| 客户端删评论 | story.commentCount -1（min=0），hotScore 更新 |
| 调 `recomputeHotScores` | 全表 story.hotScore 按当前时间重算 |

- TypeScript 文件按"firebase-functions v2 + admin SDK v13"标准 API 写，**未实地 build 过**（与 T1.4 dry-run 策略同口径）；实际 `npm install` + `tsc` 在 Windows 端跑

### Windows 端 emulator 手测（D9–D12 完成 T1.6 emulator 拉 JAR 后顺道做）

```powershell
cd D:\wsl-share\Algorithm\functions
npm install                 # 一次性
npm run build               # tsc 编译到 functions/lib/
cd ..
firebase emulators:start --only firestore,auth,functions
```

最小用例：

1. Emulator UI（http://localhost:4000）手工建 1 个 story（`visibility=public`，无 likeCount/commentCount/hotScore）
2. **预期 2 秒内**：该 story 出现 `likeCount=0` / `commentCount=0` / `hotScore≈5`（onStoryCreated 起效）
3. 手工在 `stories/{id}/likes/<uid>` 写一条文档
4. **预期 2 秒内**：父 story `likeCount=1`，`hotScore` 由 5 升至 ≈ 7
5. 手工删该 like 文档 → `likeCount=0`，hotScore 回落
6. 同样跑评论的 create/delete
7. PowerShell 打 HTTP 调 Callable：

   ```powershell
   Invoke-RestMethod -Uri 'http://127.0.0.1:5001/inkite-demo/asia-east1/recomputeHotScores' `
     -Method Post -ContentType 'application/json' -Body '{"data": {}}'
   ```

   返回 `result=@{recomputed=1}`，story 的 hotScore 按当前时间重算（freshness 略下降）

成功 = T1.7 在线下闭环。
